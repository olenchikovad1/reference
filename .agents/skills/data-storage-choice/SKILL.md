# Выбор хранилища

## Главное правило

**Сначала расширяем PostgreSQL, и только потом добавляем систему.**

Каждое дополнительное хранилище стоит не установки, а эксплуатации: бэкапы,
восстановление, мониторинг, миграции, версии, экспертиза в команде. И главное —
**между двумя системами нет ни соединений, ни транзакций**. Данные, которые
раньше можно было связать запросом, придётся связывать кодом и сверять.

Для небольшой команды это обычно перевешивает любой выигрыш по производительности.

## PostgreSQL — по умолчанию

Реляционная модель, транзакции, ограничения в схеме, JSONB, расширения. Этого
хватает подавляющему большинству прикладных задач.

Postgres при правильных индексах и секционировании спокойно живёт на сотнях
миллионов строк. «Не потянет» — гипотеза, которую надо проверять на своих
данных, а не принимать на веру.

## Документы: JSONB, а не отдельная база

**JSONB достаточно, когда:**

- структура меняется, но данные всё равно связаны с остальной моделью и
  участвуют в тех же запросах;
- документ — **часть** сущности: настройки, полезная нагрузка, снимок ответа
  внешнего API;
- нужны транзакции вместе с реляционными данными.

JSONB индексируется (GIN), поддерживает поиск по вхождению и по пути. Слабое
место — частые точечные обновления внутри больших документов и сложные
многоступенчатые агрегации.

**Отдельная документная база (MongoDB) оправдана, когда:**

- документ — сама единица работы: читается и пишется целиком;
- структура записей действительно разнородна, устойчивого ядра нет;
- нужно горизонтальное шардирование с самого начала.

**Чего это стоит:** вторая система в эксплуатации и отсутствие соединений с
реляционными данными. Если в задаче есть слово «и связать с», ответ почти
всегда JSONB.

## Векторы: pgvector, а не отдельная база

**pgvector достаточно, когда:**

- объём — сотни тысяч, единицы миллионов векторов;
- поиск фильтруется метаданными («похожие среди активных товаров этого
  бренда») — **главный аргумент**: в отдельной векторной базе метаданные
  придётся дублировать и синхронизировать;
- требования к задержке обычные, не десятки миллисекунд при высокой нагрузке.

Индекс HNSW строится долго и занимает память — это учитывается заранее.

**Специализированная векторная база (Qdrant, Milvus, Weaviate) оправдана,
когда:** десятки миллионов векторов и выше, высокая частота запросов с жёсткой
задержкой, нужны гибридный поиск и квантование.

## Аналитика: ClickHouse — дополнение, а не замена

**Подходит, когда:**

- запросы аналитические: агрегация по сотням миллионов событий;
- данные только дописываются, не обновляются, упорядочены по времени;
- отчёты и дашборды, на которых Postgres начинает считать секундами.

**Не подходит для:** транзакционной нагрузки, точечных обновлений, логики с
множеством соединений, небольших объёмов.

ClickHouse **живёт рядом** с основной базой и наполняется из неё. Заменять им
OLTP-хранилище — ошибка категории: это разные инструменты, а не разные версии
одного.

## Правило принятия решения

Вопросы по порядку, до первого «да»:

1. Данные связаны с остальной моделью и участвуют в общих запросах? →
   **Postgres**, при переменной структуре — JSONB.
2. Нужен поиск по векторам? → **pgvector**, пока объём и нагрузка это
   позволяют.
3. Аналитика по событиям в объёме, который Postgres тянет плохо **на
   проверенных данных**? → **ClickHouse рядом**.
4. Документ — единица работы, связей с реляционными данными нет? → документная
   база.

«Postgres тянет плохо» — измеренный факт с планом запроса, а не ощущение.

Выбор оформляется решением с отвергнутыми вариантами
(`docs-decisions`) и попадает в целевой стек (`docs-context-files`).

## Проверка

- назвать причину выбора хранилища — она из правила, а не из моды;
- посчитать, сколько систем придётся сопровождать, — число названо осознанно;
- проверить, решается ли задача уже имеющимся хранилищем, — проверено до
  добавления нового.

## Чего не делать

- заводить новое хранилище, не посчитав цену сопровождения;
- брать специализированное решение там, где хватает имеющегося;
- выбирать по популярности, а не по свойствам задачи.

## Смежное

- `data-access` — как к выбранному хранилищу обращаются из кода.
- `data-schema` — ограничения и индексы в реляционной части.
- `docs-context-files` — новое хранилище это решение по стеку с ценой.

## Отступления в этом проекте

Пока нет.

Правило перенесено из общей библиотеки. Если проекту оно подходит не целиком,
текст правила **не режется** — отступление записывается сюда, отдельным
блоком:

    ### <к какому пункту правила> — <дата>

    **Отступаем:** что делается иначе.
    **Потому что:** причина. Без причины отступление не действует — оно
    неотличимо от забытой правки.

Отступление читается как часть правила: код, соответствующий ему, находкой не
считается. Наверх, в библиотеку, оно не поднимается — это специфика проекта, а
не общее правило.

Больше трёх отступлений здесь означают, что правило проекту не подходит
целиком: это повод пересмотреть его, а не дописать четвёртое.
