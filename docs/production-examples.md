## Что переносится

В локальном томе PostgreSQL найдены 150 карточек и 152 неизменяемые версии,
182 записи векторов библиотеки, 26 слоганов. Архив S3: 1056 объектов,
114 380 800 байт. Это сохранённая работа, включая снимки сторон и замечания,
а не повторная случайная генерация карточек.

`scripts/stand/transfer_examples.py` переносит сохранённые данные по явному
списку таблиц. Личные черновики, порядок карточек пользователя, доступы,
проекции людей и журналы переразметки не переносятся. Локальные справочники
не копируются: сверяются уже существующие фикстуры-зависимости карточек.
Справочники PLM читаются live по решению 0018.

Запуск в контейнере API с томом `/transfer`:

```sh
python -m scripts.stand.transfer_examples export /transfer/examples.tar
python -m scripts.stand.transfer_examples check /transfer/examples.tar
python -m scripts.stand.transfer_examples import /transfer/examples.tar --apply
```

Перед production-импортом сохраняется `pg_dump -Fc` целевой базы.
Сначала добавляются файлы с проверкой SHA-256, затем одной короткой
транзакцией — отсутствующие строки и связи. Конфликт прекращает импорт;
существующая работа не перезаписывается. Повтор проверяет содержимое и
не добавляет дубли. Обрыв до транзакции оставляет только непривязанные файлы.
Аудиозамечания используют отдельную ступень `audio`.

Длительные export/check/import запускаются отдельным фоновым процессом;
конечный JSON и код завершения сохраняются в журнале запуска. При проверке
production нужны список карточек, открытие версии, снимки сторон и исходные
элементы через `thumb`/`preview`, а не только health.

Выпуск палитры совместим с прежними версиями данных: миграции нет,
контракт `/colours` прежний. Откат кода выполняет установка; импортированные
примеры остаются читаемыми. Удаление импортированных карточек при откате
автоматически не выполняется: после импорта в них могла появиться новая
работа. Резервный снимок восстанавливают только отдельным решением владельца.

## Что действительно есть в PLM

Проверка production машинным входом: 2661 цвет, 17 активных дропов,
коллекции с фабриками, моделями, цветомоделями, галереями и размерными рядами.
Рабочая палитра `/colours` берёт коды и RGB из PLM; цвет без RGB не
превращается в выдуманный оттенок. Локальная палитра допустима только для
автономного стенда. Отказ PLM возвращается явно, без подмены справочника.

`scripts/garment/probe_plm_frames.py --releases 8` проверил 100 моделей:
45 белых вариантов с изображениями; распознаны 57 передних, 34 задних,
33 левых и 32 правых рендера. Ещё у 581 изображения сторона не распознана.
Например, модель 2871, WHITE: четыре стороны лонгслива; есть также белые
Лотта-рендеры 0422 и 0425 с русскими названиями сторон.

Все шесть ограниченных проб скачивания через машинный вход дали HTTP 500.
Причина подтверждена traceback PLM: `machine_image` вызывает `images_api.image`
без нового обязательного аргумента `request`. Это дефект входа PLM,
а не отсутствие рендеров. Исправление требуется в проекте PLM по его маршруту.
Скрипт сохраняет отказы в отчёте и не объявляет прозрачность проверенной.

Из машинного паспорта приходит имя размерного ряда, но `sizes`, `size_charts`
и `images` пока пусты; галереи приходят в карточке коллекции. Для точной
примерки также нужны физические мерки, базовый размер и калибровка каждого
ракурса. Белый рендер сам по себе не определяет сантиметры. Следующий полезный
шаг: исправить скачивание в PLM, распознать русские стороны и открыть табели
мер машинным входом; затем заводить проверенные изделия с калибровкой.
