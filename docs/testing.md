```sh
python3 scripts/testing/run.py --stage change --base origin/master
python3 scripts/testing/run.py --stage change --changed web/src/shared/plmCanvas.ts --regression REF-WEB-shared.plmCanvas

```

В Windows вместо `python3` — установленный Python. API и frontend проверяются
в Docker. `--state-dir` либо `REFERENCE_TEST_STATE` задаёт устойчивую историю;
по умолчанию `~/.cache/reference-testing`, вне checkout. `--output` задаёт новый
каталог свидетельства: существующий `evidence.json` не перезаписывается.

## Каталог и выбор

`scripts/testing/catalog.json` задаёт ядро, регрессии, области и бюджет.
`catalog.py` перечисляет настоящие тестовые файлы: новый файл получает
стабильный ID и входит в обход. Риск backend-группы берётся из предметного
docstring. Проверяется наличие всего ядра и уникальность ID.

Ядро защищает селектор, черновики, стороны и холст PLM, запрет стендового
режима в production, серверные права и сохранение/восстановление work через
API/БД с неизменяемой первой версией.

Выбор: `core ∪ affected ∪ regressions ∪ previous_failures ∪ due_rotation`,
затем остаток по давности в бюджете. Seed переставляет только равные по
давности группы. Неизвестный изменённый путь расширяет набор целиком.
Изменённый отпечаток входов включает группу даже при пробеле карты влияния.
Общие исходники, зависимости, права, схема и инструментарий расширяют проверку
на потребителей. Необязательный остаток и причина пропуска видны в отчёте.

Без истории всё считается непроверенным. Максимальная давность успеха —
**семь суток**. Падение и пропуск не обновляют `last_success`.
## Предохранители ротации

Контроллер и все его Docker-контейнеры принадлежат одному ограниченному
cgroup. Для Docker с драйвером systemd используется
[`reference-testing.slice`](../deploy/testing/reference-testing.slice)
(`MemoryMax=2G`, `MemorySwapMax=0`), для cgroupfs — `/reference-testing`
с теми же ограничениями. Вход проверяет файлы лимитов ядра, членство
контроллера и размещение пробного контейнера. Для cgroup v1 дополнительно
требуются совпадающие лимиты RAM и RAM+swap и `memory.swappiness=0`.
Вложенные Docker-контейнеры получают явный `--cgroup-parent`.
API ограничен 1152 МиБ, Vitest — 768 МиБ, PostgreSQL — 320 МиБ,
MinIO — 256 МиБ. Индивидуальные контейнеры тоже запускаются без swap.

Исполнитель заранее получает тестовые образы того же checkout и образы
тестовых PostgreSQL/MinIO. Ротация использует локальный Docker Unix socket
и не собирает и не скачивает образы. При несовпадении отпечатков образов,
отсутствии лимита или неготовых образах она завершится с ошибкой до тестов.
Включать вход следует на выделенном исполнителе вне боевого sandbox.
Его администратор устанавливает slice в `/etc/systemd/system/` и запускает
контроллер внутри этой slice с правами пользователя runner. Для ручной
приёмки на таком исполнителе:

```sh
export REFERENCE_ROTATION_ENABLED=1
export REFERENCE_TEST_STATE="$HOME/.cache/reference-testing"
sudo systemd-run --wait --pipe --collect --slice=reference-testing.slice \
  --uid="$(id -u)" --working-directory="$PWD" \
  --setenv=REFERENCE_ROTATION_ENABLED=1 --setenv="REFERENCE_TEST_STATE=$REFERENCE_TEST_STATE" \
  bash deploy/testing/rotation.sh --image api=reference-tc-api:TAG --image web-test=reference-tc-web-tests:TAG
```

Предел ротации — 600 секунд вместе с подготовкой и уборкой. На 585-й секунде
контроллер прерывает проверки и начинает уборку. Недовыполненное обязательное
остаётся отказом в `evidence.json`, а не принятым прогоном. Приёмка
подключения в Installation требует успешного обычного профиля, проверки
отказа на лимите вне sandbox и сохранения доказательств как артефакта.

## Тяжёлое и reuse

Тесты с настоящими эмбеддингами, разметкой и Whisper отнесены к профилю
`models`. Обычный профиль сохраняет проверки API и бизнес-логики, запускается
без скачивания и монтирования весов. Модельная проверка запускает один
явно выбранный файл в отдельном контейнере до 1408 МиБ и пишет свою историю:

```sh
python3 scripts/testing/run.py --stage models --model-group REF-API-voice_model --image api=reference-tc-api:TAG
```

Для неё нужен тот же защищённый Linux-исполнитель. Вес и модельный кэш
готовятся отдельно от ежедневного прогона. Каждый backend-файл получает свой
процесс, БД и S3-ведро: данные и event loop соседнего файла не влияют на него.
Frontend идёт одним Vitest-пакетом. Общие вычисленные словари моделей
сохраняются отдельно с SHA-256 и происхождением (образ, модели, зависимости,
конфигурация, Docker engine); это кэш вычислений, а не успешных тестов.
Нулевой набор, ошибка сбора и пропущенный обязательный
тест не превращаются в зелёный результат.

Ключ группы содержит содержимое исходников, тестов и селектора, фактически
установленные зависимости, Python/Node/ОС, тестовую конфигурацию, миграции и
данные. Модели проверяются по SHA-256 описи. Frontend сохраняет отпечаток
установленных файлов зависимостей в `build-inputs.json` внутри сборки.
SHA Git и тег сами по себе ключом не являются; merge без изменения содержимого
не заставляет повторять независимую проверку.
У API учитываются content digests всех runtime-слоёв, архитектура, ОС и
полная runtime-конфигурация. Image ID записывается отдельно: BuildKit
attestation меняет его даже при неизменном исполняемом содержимом. Новый
ID всегда проходит приёмку кандидата, но сам по себе не обнуляет тесты.
Принятый снимок хранит также хеши исходных файлов: новый shallow clone
installation сравнивается с ним без требования старого Git-коммита в клоне.
Нет принятого снимка — влияние неизвестно, набор расширяется целиком.

`reused` допускается только для непросроченного успеха с точно теми же
известными входами. Указывается исходное свидетельство; время успеха не
обновляется. Первый отказ остаётся отдельным неизменяемым отчётом.
Исчезновение истории вызывает проверку, а не неподтверждённый reuse.

## Отдельный воркер Whisper

Наложение [compose.sandbox.voice.yaml](../infra/compose.sandbox.voice.yaml)
переносит потребителя голосовой очереди в отдельный контейнер. API по-прежнему
принимает аудио и ставит задачи в RabbitMQ. Воркер читает только каталог Whisper,
получает только настройки БД, S3 и RabbitMQ, имеет свой тег,
предел 896 МиБ без swap и два потока по умолчанию. Учетные данные воркера
можно задать отдельно в окружении Installation по [образцу](../infra/voice.env.example).
Готовность отмечается после регистрации потребителя в очереди.

Штатная выкладка Installation пересоздаёт API с наложением, ждёт готовности,
затем поднимает `voice`. Для отдельного обновления заранее доставьте образ
`reference-api`, укажите его тег в `REFERENCE_VOICE_TAG` и пересоздайте
только `voice`. Откат Installation останавливает `voice` до запуска
прежнего API со встроенным потребителем.

## Отдельный контейнер CLIP

[compose.sandbox.clip.yaml](../infra/compose.sandbox.clip.yaml) добавляет
контейнер эмбеддингов изображений с пределом 640 МиБ, нулевым swap и двумя
потоками. Он получает только веса, опись и том Unix-сокета. На старте
проверяется SHA-256 весов. API отправляет тензор 1×3×224×224 float32
по `POST /v1/encode` и получает идентификатор модели и 512 чисел.
Адрес сокета задаётся наложением. При недоступности воркера API
возвращает обычный отказ недоступности модели.

Выкладка ждёт готовности `clip` перед переключением API. По умолчанию оба
воркера используют тег релиза. Для обновления только CLIP заранее доставьте
образ `reference-api`, укажите его тег в `REFERENCE_CLIP_TAG` и
пересоздайте только `clip`. Откат Installation останавливает `clip` после
возврата базового API. Откат сохраняет тома и схему.

## Кандидат и две машины

`build.sh` собирает образы и записывает commit/tag кандидата в Git metadata.
Installation затем вызывает `unit.test → test.sh`: профиль принимает ровно
эти API/web/tunnel-образы до ship/apply. Без записи кандидата `test.sh` запускает
профиль изменения. Устаревшая запись другого коммита вызывает отказ.
`test.sh` фиксирует image IDs до проверок; дополнительно сравнивает `/tunnel.sh`
в образе с исходником и запускает его OpenSSH. Это проверка транспортного
артефакта; настоящее межмашинное SSH-соединение ею не заявляется.
Image IDs записываются; другой digest получает новую приёмку. Несовпадение
зависимостей frontend с проверенными останавливает приёмку.

Кандидат работает в приватной Docker-сети с одноразовыми PostgreSQL/pgvector
и S3. Рабочие env/БД/ключи не подключаются. Настоящий nginx отдаёт собранный
frontend и корневой `/manifest`, передаёт `/reference/api/` на адрес
`reference-tunnel:8031`; настоящий API сохраняет и перечитывает синтетический
work v3 в отдельной БД. Это HTTP-контракт частей. Реальный межмашинный SSH и
вход человека через платформу здесь не заявляются; серверные права отдельно
проверяются настоящими маршрутами с тестовыми JWT.

## Свидетельства и границы

`evidence.json` содержит договор, commit/tree и dirty, этап, seed, все выбранные
ID и причины, версии тестов, входы, executed/reused/failed, источник reuse,
`last_success`, просрочки, подготовку/исполнение/wall-clock и бюджет. Исходные
JSON/XML раннеров и логи лежат рядом. Только собственные временные контейнеры
и сеть удаляются; журнал и история сохраняются.

Обязательные PLM/PLATFORM scenario/visual/rollout относятся к sensitive
соседних проектов. Reference их не присваивает; существующие снимки браузера
не называются автоматическим сравнением с эталоном. Первая загрузка моделей
и зависимостей требует сети и входит в подготовку. Неизвестный вход запрещает
reuse. Проверочные записи в production запрещены.
