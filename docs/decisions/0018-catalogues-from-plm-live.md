# 0018. Каталог выпуска — из PLM live, без зеркала в Reference

**Дата:** 09.10.2026
**Пересматривает:** [0013](0013-own-catalogues-forever.md) целиком
**Касается:** домен `drops` / клиент PLM, витрина, связи референса с
цветомоделью и дропом, терминология в AGENTS.md, наполнение prod
**Не касается:** Cosmic и `scripts/cosmic/` (рудимент, не трогать); кадров
примерки из PLM (их там нет в пригодном виде)

## Задача

Наполнить prod Reference реальными выпусками, цветами и цветомоделями.
Источник правды о каталоге — hub PLM (`D:\Проекты\Laretto\plm`, код
приложения `plm`), не Cosmic и не собственная копия справочников в Postgres
Reference. Решение 0013 («свои, навсегда») сознательно отменяется: единая
правда о выпусках нужна уже сейчас.

## Решено

**Reference читает каталог PLM по API (предпочтительно) или периодическим
обращением к БД PLM; пинг допустим. Строки дропов, пантонов и цветомоделей в
свою базу не копирует и не дублирует.**

В карточке референса и в фильтрах витрины хранятся и передаются **внешние
идентификаторы PLM** (код дропа, id цветомодели / модели), а не локальные
суррогаты зеркальных таблиц. Подписи, недели отгрузки, цвет, фабрика —
добираются запросом к PLM в момент показа или коротким кешем ответа, не
материализацией справочника.

**Что обязательно брать из PLM (live):**

| Что | Ориентир API | Право |
|---|---|---|
| Дропы / выпуски | `GET /plm/api/directories/drops/items` | `dictionaries:view` |
| Пантоны / цвета | `GET /plm/api/colors` (+ при необходимости `GET /plm/api/catalog/pantone-search`) | `colors:view` / `models:view` |
| Цветомодели и модели | `GET /plm/api/catalog/styles`, `…/colorways`, `…/colorways/{id}` | `models:view` |
| Фабрика и смежное по модели | карточка цветомодели: `releases[].supplier_id`, список `suppliers`; при необходимости `GET /plm/api/suppliers` | `models:view` / `suppliers:view` |
| Картинки PLM (только справочный показ, не холст) | `GET /plm/api/images/{key}/{thumb\|preview}` | `models:view` |

**Связь «цветомодель ↔ дроп»** для витрины и создания референса — тоже из PLM,
не из локальной `drop_items`. Пока контракт карточки отдаёт `drop_code` слабо
(см. пробелы ниже) — это запрос в PLM, а не костыль зеркала в Reference.

**Термины подтягиваем к PLM, не наоборот.** Дроп в PLM — код + сезон /
подсезон / категория + недели `ship` / `intake` / `exit`. Поля Reference вида
«имя + календарные даты `release_from`/`release_to`» при чтении из PLM не
навязываются источнику: показ и фильтры говорят языком PLM.

**Артикул PLM и код изделия для кадров — разные оси.** Артикул / style code
(например `2027`) связывает работу с карточкой PLM. Код изделия с кадрами
состояний (`B-HDY-14` или новый) — свой: лежит в описании изделия и в S3 /
томе, в PLM его может не быть.

## Почему

**Единая правда о выпуске.** Дроп и цветомодель, заведённые в PLM, не должны
заводиться второй раз руками; переименование там обязано быть видно здесь.

**Зеркало — второй источник правды.** Копия в Postgres Reference расходится
молча и требует синхронизации, прав и разбора конфликтов — ровно то, от чего
0013 уходил ценой расхождения. При живом PLM цена зеркала выше цены вызова.

**Ранний аргумент 0013 («дропы появляются раньше PLM») больше не держит
наполнение prod.** Prod наполняется из уже ведущегося каталога PLM; досрочная
работа дизайнера, если понадобится, — отдельный случай (черновик без дропа /
временный внешний id), а не повод снова заводить полный справочник у себя.

## Что остаётся своим в Reference

| Своё | Где |
|---|---|
| Карточка референса, версии, черновик, корзина | домен `references` |
| Библиотека элементов принта | домен `library` |
| Кадры состояний для холста, карты/геометрия, печатные зоны, калибровка см↔px | домен `assets` / описания изделий; объектное хранилище (решение 0002), на prod — Yandex Object Storage |
| Линтер, согласование, роли в ходе, люди приложения | `checks`, `review`, `people` |
| Связь «артикул PLM → код изделия с кадрами» | своя тонкая таблица или поле на стороне Reference (только ключи и код изделия, не каталог) |

**Холст примерки из PLM не берём.** Картинки цветомоделей — цветные фото;
лекала — `.dxf` / детали кроя; `image_class` в демо пуст и как фильтр
ненадёжен. Поток кадров: команда кладёт модели (Drive / общее хранилище) →
загрузка в S3 Reference; позже часть может попадать и в PLM, но не как
источник холста сегодня. Табели мер PLM (`size_charts`) — опционально для
размерной сетки / градации, **не** заменяют печатное поле и якоря.

**Стенд** может по-прежнему держать локальные фикстуры каталога и кадров
(решение 0012) для работы без PLM. Это тестовые данные, не модель prod.

## Контракт: что Reference зовёт у PLM

Минимальный набор полей (имена — как в схемах hub):

**Дроп** (`DropItem`): `code`, `season`, `subseason`, `category`,
`description`, `ship_week_uz`, `ship_week_cn`, `intake_week`, `exit_week`,
`active`, `position`.

**Цвет** (`Color`): `id`, `code`, `code_short`, `name` / `name_ru`, `group` /
`group_ru`, `catalog`, `red`/`green`/`blue`.

**Модель** (`StyleRow`): `id`, `code`, `name`, `category` / `category_id`,
`path`, `gender`, `size_range`, `drops[]`, `image` (ключ).

**Цветомодель, список** (`ColorwayRow`): `id`, `article`, `title`,
`style_id` / `style_code`, `color`, `base_color`, `rgb`, `category_id`,
`gender`, `releases[]`, `suppliers[]` (имена, internal), `image`.

**Цветомодель, карточка** (`ColorwayCard`): всё нужное для карточки работы —
`article`, `style_*`, `color` / `color_code`, `drop_code`, `releases[]`
(`id`, `code`, `stage`, `supplier_id`), `size_range` / `sizes`, опционально
`size_charts` (градация), `prints[].pantones` (пантоны принта на карточке).
`patterns` и галерея `images` для холста **не** используем.

**Картинки PLM:** только `thumb` / `preview` для справочного показа (И-3:
оригинал в браузер Reference не тащим и отсюда тоже). Порог качества —
меньшая сторона не ниже 800 px; мельче в выбор модели не показываем.
Кадр примерки (холст) из фото PLM **не** делается — только том кадров
Reference (US-0025 / US-0887).

## Пробелы API PLM — запрос в PLM, не костыль в Reference

| Нужно Reference | Сейчас в API | Запрос в PLM |
|---|---|---|
| Надёжная связь цветомодель ↔ дроп для витрины и создания работы | В списке цветомоделей дропа нет. На карточке `drop_code` = первый непустой `OrderLine.drop_code` по релизам — **пусто, если заказов нет**. `Style.drop_code` и `ReleasePlan.drop_code` в карточку/список цветомодели не отдаются | Отдать на списке и карточке дроп(ы) цветомодели из плана релиза / стиля (или явной связи ReleaseColorway↔drop), не только из строки заказа |
| Фабрика по конкретной модели (артикул), до заказа | `StyleRow` фабрики не содержит. `releases[].supplier_id` на карточке — из **заказа**; в списке — имена `suppliers` (internal). `style_suppliers` в API списка/карточки не экспонирован | Явное поле фабрики(и) на стиле или на релизе цветомодели без требования заказа; id поставщика, не только отображаемое имя |
| Дроп на релизе в карточке | `CardRelease` — только `id`, `code`, `stage`, `supplier_id` | Добавить `drop_code` (из `ReleasePlan`) на элемент `releases[]` |
| Ассортимент «дроп → цветомодели» одним запросом | Нет матричного эндпоинта; собирается обходом списков | Желательно: `GET …/drops/{code}/colorways` или фильтр `colorways?drop=` — иначе Reference будет N+1 по каталогу |

Пока пробелы открыты, Reference **не** заводит локальные таблицы «чтобы жить».
Допустимы: повторный запрос, короткий кеш ответа, и явный статус «дроп/фабрика
в PLM ещё не проставлены».

## Минимальный план наполнения prod

Без копирования дропов и цветомоделей в Postgres Reference.

1. **Доступ.** Сервисный субъект платформы с аудиторией `plm` и грантами
   `dictionaries:view`, `models:view`, `colors:view` (при показе фабрик —
   `suppliers:view`). Тот же контур, что у других приложений платформы; вход
   Reference→PLM — JWT субъекта, не свой логин в PLM.
2. **Клиент PLM** в Reference (`api-external-calls`): базовый URL `/plm`,
   таймауты, разбор стабильных кодов отказа; вызовы только из сервисного слоя /
   BFF, не из браузера с чужими секретами.
3. **Схема Reference.** Убрать зависимость prod-пути от локальных
   `drops` / `colour_models` / `drop_items` как источника правды: на карточке —
   внешние ключи PLM; тонкая связь «style/colorway PLM → `product_code`
   изделия с кадрами». Миграция данных стенда — отдельно, стендовые фикстуры
   остаются для демо.
4. **Кадры примерки в S3.** Скрипт в `scripts/` (не `python -c`): приём
   кадров из согласованного хранилища команды (Drive → файлы) → Yandex Object
   Storage по правилам 0002 (имя по хешу); описание изделия с калибровкой и
   зонами — как у `B-HDY-14`. Пока кадров на артикул нет — референс на нём не
   создаётся (как сейчас при пустом `product_code`).
5. **Витрина / фильтры.** Дропы и матрица ассортимента — live (или кеш
   ответа); после закрытия пробелов API — без обходных зеркал.
6. **Не делать:** импорт Cosmic; одноразовый разбор вне `scripts/`; загрузка
   лекал/фото PLM как кадров холста; дублирование `GET /api/colors` в
   `palette.yaml` на prod.

## Рассмотрено и отклонено

**Оставить 0013 («свои, навсегда»).** Отклонено владельцем при разведке
наполнения prod: расхождение с PLM и двойной ввод каталога недопустимы.

**Зеркало PLM → таблицы Reference по расписанию.** Отклонено: второй источник
правды, рассинхрон, те же права и простой чужого контракта плюс стоимость
синхронизации. Периодический пинг/чтение **без** материализации строк — допустим.

**Брать кадры холста из `GET /api/images` и лекал PLM.** Отклонено по проверке
на модели 2027 в демо PLM: нет обесцвеченных состояний VStitcher, нет
калибровки см↔px и печатных зон; лекала — крой, не холст.

**Продолжать наполнять палитру из Cosmic (`scripts/cosmic`, `palette.yaml` как
prod-истина).** Отклонено: Cosmic — рудимент; цвета — `GET /api/colors` hub.

## Повод пересмотреть

- PLM отдаст пригодные кадры состояний с калибровкой и зонами — тогда поток
  Drive→S3 можно сузить или частично заменить чтением из PLM.
- Платформа введёт общий каталожный сервис выше PLM — тогда клиент Reference
  переключается на него, правило «не зеркалить» остаётся.
