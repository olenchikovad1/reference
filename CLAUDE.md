# Референс — правила работы

Приложение платформы: вся работа с принтами от «вот интересная картинка» до
файла на фабрику. Принт примеряется на изделие, система сама проверяет
геометрию, согласование идёт письменно.

Подключается к платформе (`C:/Projects/platform`) как самостоятельное
приложение: код `reference`, манифест — `manifest.reference.yaml`. Субъекты,
права, вход и журнал действий живут на платформе; здесь их нет.

Выборы и основания — в [docs/decisions](docs/decisions/README.md). Правила
разработки — в `.claude/skills/` (28 правил). Этот файл про устройство и
инварианты и не пересказывает ни то, ни другое.

## Терминология

Помечено, внутренний термин или общепринятый.

| Термин | Вид | Значение |
|---|---|---|
| **Изделие** | внутренний | Тип одежды: худи, футболка. Набор состояний, печатные поля по размерам, размерная сетка. Заводит технолог, меняется редко. |
| **Состояние** | внутренний | Изделие в одном положении: перед, спина, капюшон надет, молния расстёгнута. Кадр плюс карты плюс калибровка «см ↔ пиксели». Набор задаёт технолог на тип изделия, не дизайнер на карточку. |
| **Точный ракурс** | внутренний | Состояние, по которому считаются размещение и проверки (перед, спина). Противоположность — **иллюстративный**: только показ. |
| **Элемент библиотеки** | внутренний | Растр, текст или вектор, из которого собирается принт. Живёт годами, коллекции не принадлежит. |
| **Референс** | внутренний | Карточка: конкретный принт на конкретном изделии в конкретном цвете. Единица работы и единица согласования. |
| **Слой** | внутренний | Элемент внутри референса. Референс — дерево слоёв, не плоская картинка. Замечание вешается на слой. |
| **Печатное поле** | внутренний | Ограничение: куда физически можно печатать на данном размере, в сантиметрах. **Не** то же, что коэффициент масштабирования принта. |
| **Градация** | внутренний | Стратегия изменения принта по размерам: фиксированная (умолчание), пропорциональная, ступенчатая. |
| **Линтер референса** | внутренний | Проверки, считаемые из геометрии: печатное поле, швы, перекрытия, высота буквы, толщина линии, число цветов. Два веса — блокирующие и предупреждения. |
| **Ход** | внутренний | Чья сейчас очередь действовать. Вычисляется из статуса и ролей, отдельным полем не хранится. |
| **Техпакет** | внутренний | Выгрузка на фабрику: плоский печатный лист в сантиметрах, цвета, размещение, размеры. |
| **Проекция субъекта** | общепринятый | Снимок имени и идентификатора человека из платформы для показа «кто сделал». Только чтение, источником правды не является. |
| **Раздел, действие, функция, грант** | общепринятый (платформа) | Модель доступов платформы. Объявляются манифестом, см. `manifest.reference.yaml`. |

## Целевой стек

Целевое состояние, а не опись. Мажорная версия названа там, где её смена меняет
способ писать код.

**Бэкенд.** Python 3.13+, FastAPI, SQLAlchemy 2.x (async), Alembic, Pydantic v2,
PostgreSQL 17, RabbitMQ 4.x, зависимости через `uv`.

**Фронтенд.** React 19, Vite, TypeScript, Tailwind 4, Radix UI, TanStack Query,
TanStack Table — через пакеты `@platform/*`, а не напрямую.

**Почему именно это:** стек задан платформой. Приложение, собранное на другом,
не сможет взять её компоненты, её клиент и её оболочку, и выиграет ровно
ничего. Обоснование самого стека — в решениях платформы 0005 и 0009.

**Графика.** Композиция слоёв — Konva или fabric на холсте; смещение —
WebGL-шейдер (PixiJS `DisplacementFilter` либо свой). Тот же шейдер headless на
сервере для миниатюр и экспорта. Выбор между Konva и fabric не сделан —
делается первой историей, где появится холст, и записывается решением.

**Хранение.** Два класса, смешивать нельзя (решение 0002): исходники изделий —
файловое пространство томом, путь в базе; кадры и производные — объектное
хранилище, MinIO на стенде и Yandex Object Storage на проде, имя по хешу
содержимого.

**Поиск по похожести.** pgvector в том же PostgreSQL, отдельного векторного
сервиса не заводим, пока объём не потребует.

**Поводы пересмотреть:** платформа сменила мажорную версию пакетов; объём
библиотеки перерос pgvector; появился экспорт меша из VStitcher (тогда
пересматривается решение 0001, а с ним весь путь получения состояний).

## Устройство

### Слои первичны, домены внутри слоя

```
api/reference_api/
  models/         как данные хранятся и какие ограничения держит база
  schemas/        что принимается снаружи и что отдаётся наружу
  repositories/   как данные достаются, без бизнес-смысла
  services/       правила предметной области
  api/            контракт и права — вход по HTTP
  consumers/      разбор сообщений — вход из брокера
  schedulers/     периодическая работа — вход по расписанию
```

Внутри слоя — **файл на домен**. Слоёв мало и состав их стабилен годами;
доменов много, и границы их двигаются. Изменчивое измерение первичным не
делают. Файл слоя вырос — становится каталогом с тем же именем; ось не
меняется, меняется глубина.

**Домены:** `products`, `library`, `references`, `checks`, `review`,
`collections`, `assets`. Вход через брокер есть у `assets` и `references`, по
расписанию — только у `references`. Отсутствие файла в слое — решение, а не
недоделка.

**Три входа, не один.** `api`, `consumers`, `schedulers` — транспорт с одной
дисциплиной: каждый переводит своё представление в вызов сервисного слоя и
правил предметной области не содержит.

### Фронтенд

```
web/src/
  app/          монтирование в оболочку @platform/shell, маршруты, провайдеры
  pages/        экраны
  shared/api/   клиент /reference/api/
  candidates/   свои компоненты — только чего нет в @platform/ui
```

Компоненты и токены приходят из `@platform/ui` и `@platform/tokens`. Своё —
только в `candidates/`, и всё, что там лежит, считается кандидатом на вынос в
платформу (решение 0005).

### Стенд

Всё в докере, включая приложение. Поднимается из `infra/`:

```bash
py infra/stand/fetch_models.py && cp api/.env.example api/.env && cp web/.env.example web/.env && cp infra/.env.example infra/.env && docker compose -f infra/compose.yaml up -d --build
```

**Модель узнавания качается до подъёма, а не лежит в репозитории:** 85 МБ,
с которыми история перестаёт клонироваться за разумное время. Пропустить шаг
нельзя — стенд соберётся, а узнавание свалится в `FileNotFoundError` из недр
onnxruntime, то есть откажет невнятно. Повторный запуск ничего не качает.

**Порог узнавания меняется в `api/.env`, но контейнер надо пересоздать:**
`env_file` читается при создании, а не при каждом старте. `docker compose up -d
api` — это пересоздание без пересборки.

Порты: сервис `8010`, фронтенд `5183`, PostgreSQL `5433`, MinIO `9010`/`9011`,
RabbitMQ `5673`/`15673`. Чистое состояние — `docker compose down -v`.

**Сборка фронтенда требует запущенного стенда платформы:** пакеты `@platform/*`
ставятся из её Verdaccio через `host.docker.internal:4873` (решение 0006).

### Как ведётся работа

Основная ветка — `master`, работа идёт прямо в неё, пуш без спроса. Это
названное отступление от `process-git` с причиной и поводом пересмотра
([решение 0007](docs/decisions/0007-work-goes-straight-to-master.md)), а не
забытая настройка.

## Инварианты

Каждый назван вместе с местом проверки. Инвариант без места проверки не
выполняется.

**И-1. Размещение хранится в сантиметрах на лекале с якорем на ориентир.**
Не в пикселях. Из этого единственного источника выводятся показ, проверки,
техпакет и будущее 3D. *Проверка:* в `models/references.py` пиксельных
координат нет; ревью по `quality-review`.

**И-2. Складки не попадают в печатный файл.** Порядок строго: слои с
деформациями в плоскости лекала → плоский печатный лист в сантиметрах (он же
файл на фабрику) → отдельно карты смещения и света применяются к показу.
*Проверка:* целевой тест на то, что путь экспорта техпакета не проходит через
шейдер.

**И-3. Оригинал в браузер не уходит никогда.** *Проверка:* клиент
`shared/api/` знает только `thumb` и `preview`.

**И-4. Каждый изменяющий маршрут объявляет требуемое право.** Маршрут,
реализующий функцию, объявляет функцию, а не `write` на разделе. *Проверка:*
сервис не поднимается без объявления — контракт платформы.

**И-5. Субъекты, права и журнал действий — из платформы.** *Проверка:* в
`models/` нет таблицы пользователей; есть только проекция субъекта.

**И-6. Версии неизменяемы.** Перезаписи нет, дифф считается по слоям.
*Проверка:* в `repositories/references.py` у версии нет пути обновления.

**И-7. Отклонённое не удаляется никогда.** *Проверка:* физического удаления
карточки нет ни в репозитории, ни в API.

**И-8. Статус — не то же, что чей ход.** Ход вычисляется из статуса и ролей.
*Проверка:* «мои задачи» собираются вычислением, а не чтением поля.

**И-9. Своя папка компонентов одна — `web/src/candidates/`.** *Проверка:*
`guard_ui_boundary`, раскладка в `.claude/rails.json`.

**И-10. Исходники изделий не попадают ни в git, ни в объектное хранилище.**
*Проверка:* `.gitignore`; домен `assets` разделяет два пути явно.

## Запреты

1. **Не хранить размещение в пикселях изображения.** Из пикселей не получить
   ни спецификацию, ни переход на другой источник кадров.
2. **Не пропускать деформации показа в печатный файл.** На фабрику уйдёт не то,
   что утвердили.
3. **Не заводить свою таблицу пользователей, свой вход и свою выдачу прав.**
   Всё это на платформе, второй экземпляр расходится с первым.
4. **Не использовать генеративные модели в контуре согласования.** Они меняют
   сам принт: чуть иначе прорисуют буквы — и утверждено будет одно, отпечатано
   другое. Для маркетинговых картинок после утверждения — можно.
5. **Не класть исходники моделей в git или в объектное хранилище.** Решение 0002.
6. **Не заводить вторую папку компонентов.** Решение 0005.
7. **Не удалять отклонённые карточки и не «чистить» архив.**
8. **Не сливать таблицу печатных полей с таблицей масштабирования принта.**
   Первая — ограничение, вторая — преобразование.
9. **Не заводить статусы у слоёв.** Сознательный отказ: машина состояний иначе
   удваивается. Замечание привязано к слою и версии, статус — только у карточки.

## Когда какой скилл открывать

Условие — наблюдаемое событие, а не тема. Скилл без условия не загрузится
никогда.

**Архитектура и раскладка**

- создаю файл, хелпер, сервис или компонент; папка распухла → `architecture-placement`
- читаю переменную окружения, добавляю настройку → `architecture-configuration`
- добавляю библиотеку, обновляю зависимость, наткнулся на заброшенную → `architecture-dependencies`
- задача упала в код, которому нельзя доверять → `architecture-untrusted-codebase`

**Данные**

- пишу модель, связь, ограничение, миграцию, денежное или временнóе поле → `data-schema`
- достаю данные, открываю транзакцию, выбираю sync или async → `data-access`
- решаю, где хранить новый вид данных; тянет завести вторую базу → `data-storage-choice`

**API и внешние вызовы**

- добавляю или меняю эндпоинт, ошибку, пагинацию, версию контракта → `api-contracts`
- зову чужой сервис, ставлю таймаут, обрабатываю лимит → `api-external-calls`

**Фронтенд**

- делаю экран, беру компонент, ставлю цвет или отступ, добавляю состояние загрузки → `frontend-ui`

**Инфраструктура и эксплуатация**

- пишу Dockerfile, правлю compose, поднимаю стенд → `ops-containers`
- ставлю фоновую задачу, настраиваю повторы и очередь → `ops-background-jobs`
- добавляю лог, не могу отладить по логам → `ops-logging`
- выкладываю, откатываю, разбираю отказ на проде → `ops-release`

**Качество**

- собираюсь сказать «готово», «работает», «исправил» → `quality-verification`
- что-то сломалось, тест упал, тянет добавить заглушку → `quality-root-cause`
- пишу логику, чиню баг, который не должен вернуться → `quality-testing`
- пишу путь ошибки, ловлю исключение, пробрасываю дальше → `quality-error-handling`
- пишу сигнатуру, добавляю аннотацию, тянет поставить `Any` → `quality-typing`
- смотрю чужой или свой диф перед сдачей → `quality-review`
- правлю мешающий код, просят «прибраться» → `quality-refactoring`
- добавляю линтер, хук, гейт CI → `quality-automated-enforcement`
- трогаю секреты, вход с границы, эндпоинт, лог, зависимость → `quality-security`

**Документация и процесс**

- пишу или правлю CLAUDE.md, AGENTS.md → `docs-context-files`
- выбираю между подходами, меняю технологию → `docs-decisions`
- называю переменную, функцию, таблицу, код ошибки; пишу комментарий → `docs-naming-and-comments`
- ветвлюсь, коммичу, собираюсь пушить → `process-git`
- правлю `.gitignore`, `.gitattributes`, служебные файлы репозитория → `process-repo-service-files`

## Что известно про источник изделий

Коротко, подробно — в [решении 0001](docs/decisions/0001-garment-source.md).

Модель приходит из **Browzwear VStitcher**, не из CLO 3D. Единственное изделие
стенда — `B-HDY-14`, детская худи на молнии, размерный ряд 98–164 (не S/M/L/XL).
Описание — `infra/stand/fixtures/B-HDY-14.yaml`, файлы — в томе.

Рассчитываем **только на кадр**: прозрачный фон, обесцвеченная база. Карт
глубины, нормалей, AO и маски печатной зоны нет. Рельеф и свет выводятся из
самого кадра, печатная зона обводится полигоном в админ-режиме
([решение 0004](docs/decisions/0004-relief-from-the-frame.md)).

Чего в прототипе не будет и о чём надо говорить первыми: переключателя
состояний (состояние одно — капюшон надет, молния застёгнута), смены изображения
при смене размера (меняются только числа и рамка), точной физики деформации.

## Где сейчас проходит граница сделанного

Не список задач — он устареет. Только те места, где каркас сознательно пуст и
пустота эта означает решение, а не забывчивость.

- **Моделей нет ни одной.** `target_metadata` в `alembic/env.py` равен `None`,
  поэтому автогенерация миграций не работает — и это видно сразу, а не
  выясняется по пустой сгенерированной миграции. Первая модель приносит сюда
  свой `Base.metadata`.
- **Маршрут пока один — проверки живости и готовности.** Он же единственный, у
  которого нет объявления права, и законно это ровно потому, что прав он не
  требует. Следующий маршрут объявляет право (И-4).
- **Экран временный и будет выброшен целиком**, а не доработан. Оболочка
  `@platform/shell` придёт вместе с входом (решение 0006).
